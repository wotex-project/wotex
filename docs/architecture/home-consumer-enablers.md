# Local protocol infrastructure and exposed endpoints

This page records consumer-neutral ownership for planned additions. It does not register packages or claim implementation.

- [WUD](../packages/wotex-udp/specs/WUD-index.md): bounded generic datagrams, not an application protocol or automatic WoT binding. Existing protocol packages keep their accepted native ownership.
- [WZG](../packages/wotex-zigbee/specs/WZG-index.md): an explicit Zigbee NCP host/network/ZCL contract. The radio firmware runs the low-level stack; consumer profiles interpret device-specific attributes.
- [WMA.09](../packages/wotex-matter/specs/WMA.09-exposed-bridge-server.md): the planned Matter server/bridge role. Existing controller evidence is not server evidence. The [delivery plan](../packages/wotex-matter/plans/exposed-bridge-delivery.md) explains implementation and qualification steps.

## Integration decisions

Do not add every protocol-shaped need as a dependency of core or Runtime. A consumer-supplied HTTP client, WebSocket client or serial port can implement an existing public port. Extract a new generic package only when the lifecycle/value contract is reusable and demonstrably missing. JSON-RPC framing, vendor scenes, product catalogs and policy remain outside these transport packages.

The new planned package catalogues are design/status documents. `tooling/packages.yaml` remains the implementation graph owner; no phantom package directory is added. The generated family catalogue must be regenerated by the repository tooling when the planned packages are admitted to that graph, not edited by hand.
